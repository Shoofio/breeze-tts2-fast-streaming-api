# Performance baseline: 2026-09-24 (T002, SC-007)

The pre-change baseline that every later benchmark in this feature is compared against, using the
method in tasks.md "SC-007 method": `--warmup 3 --runs 10`, with 10-run medians compared against
10-run medians.

## Setup

- **GPU**: NVIDIA GeForce RTX 4090 (driver 596.36), WSL2.
- **Versions**: Python 3.12.12, torch 2.9.1+cu128 (CUDA 12.8), transformers 4.57.3, fastapi 0.141.1,
  starlette 1.6.0, uvicorn 0.52.4, python-multipart 0.0.32, websockets 17.1.
- **Server code**: the API from `2218c39`. `breeze_infer/api.py` was unchanged from `2218c39` up
  to `0bd1ebc` (originally `a20cfa1`, renamed by the privacy history rewrite), the HEAD when this was recorded; the commits in between add dependency pins, the
  benchmark, the harness and new modules the old API doesn't load.
- **Server command**:
  `.venv/bin/python -m breeze_infer.api <Breeze-TTS-2 snapshot c1c8ca18> --port 7860 --fast-all`
- **Benchmark command** (`bench_api` at `0bd1ebc`; defaults `--warmup 3 --runs 10`):
  `.venv/bin/python -m breeze_infer.bench_api --api old --url http://127.0.0.1:7860`

## Notes for later comparisons

- **Why the method changed.** The first recording (3 runs after 1 warm-up) had cold runs in its
  medians: medium_design's TTFA median was 223 ms, against a steady 70 ms. With 3 warm-ups the
  runs are tight, so a 10% change in a 10-run median is meaningful. Those first numbers are
  superseded and kept only in git history (`44cc760`).
- **The first recording's RTF was also about 17% worse** (0.445 / 0.413 / 0.402 against 0.369 /
  0.362 / 0.375), including its 10-run supplement, which warm-up can't explain. The cause wasn't
  measured. The likely one is that agents' full test suites (torch imports, CPU-heavy) were running
  in parallel then, and not during this recording. Because that drift is larger than the 10% gate,
  benchmarks now run with nothing else active, and record GPU clocks and power during the run
  (tasks.md "SC-007 method").
- **medium_design is one piece on both APIs.** The new segmenter keeps final text within
  `split_chars` (600) as one piece, as C++ `split_text` does; the 200-character opening budget only
  applies when the text is longer than `split_chars`. So it gates SC-007 too (decided with the user
  on 2026-09-24).
- **short_voice has no baseline.** The old API has no voices route.
